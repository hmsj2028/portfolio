# OS 신호 추출기

*2026.07 · 슈어소프트테크 인턴 · 개인 개발*

## 배경

인턴 때 주로 맡은 일은 현대케피코 VPC(Vehicle Platform Controller) HILS 검증이었다. VPC는 차체·섀시 쪽 여러 제어 기능을 하나로 묶은 제어기로, 현대차에 들어간다. 이 도구는 그 검증을 하면서 만들었다.

펌웨어가 업데이트되거나 변수가 바뀔 때마다 검증 담당자는 Simulink 모델을 직접 열어 수많은 신호 중 무엇이 바뀌었는지 하나씩 따라가야 했다. 시간이 오래 걸렸고 빠뜨리거나 잘못 읽는 일도 잦았다.

## AUTOSAR 구조를 공부하며 알게 된 것

도구를 만들려면 신호가 어디서 생겨서 어디로 가는지부터 알아야 했다. 그래서 AUTOSAR 구조를 다시 공부했다.

- **ASW(애플리케이션 계층)**: 실제 기능 로직이 들어 있는 곳이다. SWC(Software Component) 단위로 나뉘고, 모델에서 `Swc_`로 시작하는 서브시스템이 여기에 해당한다.
- **RTE(Runtime Environment)**: SWC끼리, 그리고 SWC와 아래 계층을 이어 주는 중간 다리다. SWC는 다른 SWC를 직접 부르지 않고 RTE를 거쳐 신호를 주고받는다.
- **BSW(Basic Software)**: OS, 통신 스택(COM), 드라이버처럼 하드웨어에 가까운 기능이 모여 있다.

신호는 ASW에서 정의되고 RTE와 COM 스택을 거쳐 CAN 버스로 나간다. 이 흐름을 알고 나니 모델 안에서 신호를 거꾸로 따라갈 때 어디서 멈춰야 하는지가 보였다.

헷갈렸던 건 "OS 신호"라는 말이었다. AUTOSAR OS는 OSEK/VDX 표준을 바탕으로 한 실시간 운영체제라서, 하는 일은 태스크를 언제 어떤 순서로 돌릴지 정하는 것이다. 신호를 정의하거나 보내는 계층이 아니다. 그런데 현장에서는 OS 스케줄에 맞춰 주기적으로 돌며 CAN 신호를 주고받는 로직을 모델 폴더상 `os`로 묶어 관리했고, 그래서 팀에서 "OS 신호"라고 불렀다. 표준에서 쓰는 뜻과 현장에서 쓰는 뜻이 다를 수 있으니, 용어가 나오면 어느 쪽 뜻인지 먼저 확인하는 습관이 생겼다.

## 만든 것

MATLAB으로 Simulink 모델을 자동으로 열고, 신호의 입력·출력 관계를 끝까지 추적해 엑셀로 정리하는 도구다.

- 상위 폴더만 지정하면 `os`, `rte` 등 관련 폴더를 재귀 탐색해서 모델과 데이터를 스스로 찾는다
- 모델 안의 `Swc_` 서브시스템을 찾아 들어가 실제 신호가 시작되는 지점까지 추적한다
- Goto/From, 게이트, 변환 블록을 여러 번 거쳐도 원본 신호 이름까지 따라간다
- 연결 안 된 신호(Ground), 상수, 여러 신호가 합쳐지는 경우를 구분해서 표시한다
- 여러 모델을 한 번에 처리하고 결과는 모델별 시트로 나눈 엑셀 하나로 낸다
- 진행률 창을 띄우고 문제가 생긴 부분만 로그로 남긴다

## 만든 방식

Claude Code로 요구사항을 프롬프트로 구체화하며 코드를 작성했고 실사용자 피드백(예: "입력이 여러 개인 경우도 넣어 달라")을 받아 v0.3부터 v0.6까지 기능을 넓혔다. 신호가 특이한 블록을 거치면 추적이 끊기는 경우가 있었는데, 실제로 끊기는 사례를 모아 예외 처리를 하나씩 추가해서 해결했다.

배포까지 고려해 소스를 pcode로 보호하고 실행용 .bat과 사용설명서를 만들어 "누구나 쓸 수 있는 도구"로 마무리했다.

## 결과

- 사람이 몇 시간 걸리던 신호 추적을 몇 초 ~ 몇 분으로 줄임
- 실제 검증 업무에 사용

## 배운 것

- 신호 흐름(ASW → RTE → COM → CAN)을 구조로 이해하고 나니 추적 로직을 어디서 끊어야 할지가 분명해졌다. 도메인을 알아야 도구도 제대로 만든다
- 도구는 만든 사람이 아니라 쓰는 사람 기준으로 완성된다. 설명서와 배포 방식까지가 개발이다
- 끊기는 사례를 실제로 모아야 예외 처리를 제대로 할 수 있다
