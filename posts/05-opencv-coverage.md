# 다운사이징된 OpenCV 커버리지 검증

*2026.08 ~ 2026.09 · 슈어소프트테크 인턴 · 고객사 검증 프로젝트*

## 무엇을, 왜

ADAS 시스템은 자원이 적고 ISO 26262 같은 기능안전 규격을 따라야 한다. OpenCV를 통째로 쓰면 인증해야 할 코드가 너무 많아서 **실제로 쓰는 함수만 남기고 나머지를 삭제(다운사이징)**한다. 그리고 남은 코드가 제대로 동작하는지 커버리지로 증명해야 한다.

내 역할은 다운사이징된 OpenCV를 ARM64 타깃으로 크로스컴파일하고 QEMU 에뮬레이터에서 실행해 statement / branch / function 커버리지를 gcovr로 측정·문서화하는 일이었다. 대상은 core, imgproc, calib3d, features2d, video 5개 모듈이다.

## 가장 큰 제약

삭제된 코드를 되살리면 안 된다. 그런데 OpenCV 기본 테스트는 삭제된 함수를 필요로 해서 **링크 단계에서 전부 실패**했다. 그래서 살아남은 API만 부르는 테스트를 처음부터 새로 썼다.

## 결과

| 모듈 | Line | Function | Branch |
|---|---|---|---|
| video | 99.2% | 100% | 81.5% |
| calib3d | 96.7% | 95.8% | 81.6% |
| features2d | 94.0% | 92.3% | 86.8% |
| imgproc (진행 중, 규모 20배) | 45% → 68% | 52% → 74% | 31% → 47% |

신규 테스트 수백 개를 작성했고 원인까지 밝힌 결함 5건을 보고했다. 채우지 못한 커버리지는 억지로 채우지 않고 왜 도달할 수 없는지 근거 문서로 남겼다.

## 테스트를 믿을 수 있게 만든 규칙

AI로 만든 커버리지 테스트는 "줄을 실행하는 것"에만 집중하고 값이 맞는지는 안 볼 수 있다. 실제로 초반에 얕은 테스트 뒤에 진짜 결함이 숨어 있었다. 그래서 규칙을 세웠다.

1. **정답이 있으면 반드시 값으로 검증.** 예: 순수 파란색 BGR을 HSV로 바꾸면 H=240이어야 한다. 예외가 안 나는지만 보고 끝내지 않는다
2. 정답이 없는 탐색형 테스트는 "크래시 없이 실행"이 기준
3. 남아 있는 원본 OpenCV 테스트의 시나리오를 최대한 따라 한다
4. 작성 → 감사 → 사람 확인 → 측정 순서를 건너뛰지 않는다
5. 결함처럼 보여도 실제 출력값을 이론 정답과 대조하기 전엔 단정하지 않는다

## 기억에 남는 사례

- **가장 흔한 호출이 깨져 있었다.** `connectedComponents(img, labels)`처럼 인자 없는 기본 호출이 예외를 던졌다. 추적해 보니 알고리즘 분기가 거의 삭제돼 있고 살아남은 조합은 딱 하나였다.
- **헤더는 있는데 구현이 없다.** 기하 변환 함수 5개가 선언만 남고 구현이 삭제돼 있었다. `nm`으로 심볼을 확인해 링크 순서 문제가 아니라 진짜 삭제임을 확정했다.
- **멈추는 버그.** 한 함수가 빈 이미지가 아닌 모든 입력에서 무한루프에 빠졌다. 타임아웃으로 100% 재현을 확정하고 해당 테스트는 비활성으로 문서화했다.
- **계측이 거짓말을 했다.** `-O3` 최적화로 함수가 인라인되면서 일부 코드가 커버리지에 안 보였다. 해당 파일만 `-O0 -fno-inline`으로 다시 컴파일해 정확한 값을 얻었다.
- **내 오판을 내가 잡았다.** 변수명만 보고 "R/B가 뒤바뀐 결함"이라고 판단했다가, 실제 출력값을 색 이론 정답과 대조해 정상임을 확인하고 정정했다.
- **몇 시간 헤맨 원인이 내 캐시였다.** 커버리지가 갑자기 떨어져 보여서 데이터 유실을 의심했는데, 요약 스크립트가 몇 시간 전 결과를 계속 보여 주고 있었다. 이후 수치는 항상 새로 측정했다.

## 배운 것

- 숫자보다 "왜 그 숫자인지 설명할 수 있는지"가 검증의 핵심이다
- 이상한 결과가 나오면 대상보다 측정 도구부터 의심한다
- 크래시나 무한루프가 나는 테스트는 따로 떼어 둔다. 한 프로세스가 죽으면 같은 바이너리의 계측 데이터가 다 사라진다

*고객사 프로젝트라 코드와 상세 자료는 공개하지 않습니다.*
